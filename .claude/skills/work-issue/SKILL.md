# 이슈 작업

1. `gh issue view N --comments`로 이슈와 댓글을 읽는다. 앞 세션이 남긴 댓글(브랜치, PR, 확인한 것, 남은 문제, 다음에 할 일)이 있으면 거기서 이어 간다.
2. 루트 [AGENTS.md](../../../AGENTS.md), [docs/decisions.md](../../../docs/decisions.md)의 관련 결정, [docs/progress.md](../../../docs/progress.md)를 읽는다.
3. `main`에서 이슈 번호가 들어간 브랜치를 만든다.
4. 동작을 바꾸는 구현은 확인 조건의 대표 테스트를 먼저 쓰고 실패를 확인한다. 검증기·스크립트 테스트는 확인 조건의 대표 입력을 쓰고, 기대값은 대상 코드·데이터를 직접 읽어 정한다. 문서·절차 변경은 확인 조건별 대조 위치·방법·결과로 확인한다.
5. 구현하고 4단계의 테스트로 통과를 확인한다. 구현 중에는 바꾼 부분의 테스트만 돌린다.

   아래에서는 멈추고 개발자에게 묻는다.
   - 결과가 갈리는 선택: 선택지별 결과를 보여 준다. 개발자가 고른 답은 이슈의 확인 조건과 [docs/decisions.md](../../../docs/decisions.md)에 더한다.
   - 유료 모델 호출: 이유와 횟수를 밝히고 답을 기다린다.
6. PR 직전에 바꾼 쪽의 전체 테스트와 `python scripts/check_shared_files.py`를 한 번 통과시킨다. 실행 명령은 [README](../../../README.md)를 따른다. 검사한 커밋과 명령·결과를 PR에 남긴다.
7. 단계를 마치는 이슈면 [docs/progress.md](../../../docs/progress.md) 갱신을 같은 PR에 넣는다.
8. [PR 양식](../../../.github/pull_request_template.md)대로 PR을 연다. 종류는 제목의 AngularJS type으로 나타낸다. 확인 조건별 테스트 또는 확인 근거와 이슈에 없이 스스로 정한 것을 빠짐없이 적는다.
9. [PR 검토 Skill](../review-pr/SKILL.md)의 절차대로 구현 대화를 이어받지 않은 새 세션에 검토를 맡긴다.
10. 검토 지적은 아래 "지적 처리"를 따른다.
11. 검토와 CI가 통과하고 개발자가 승인하면 스쿼시 병합한다.

이슈를 끝내기 전에 세션을 닫게 되면, 이슈에 댓글로 브랜치와 PR, 확인한 것, 남은 문제, 다음에 할 일을 남기고 [docs/progress.md](../../../docs/progress.md)의 "지금 위치"를 갱신한다.

## 지적 처리

1. 지적마다 수정 커밋과 확인 방법·결과, 고치지 않는 이유, 또는 후속 이슈 링크를 PR 댓글로 남긴다. 여러 지적은 한 댓글에 묶어도 된다.
2. 수정 확인은 고친 테스트와 영향받는 테스트만 돌린다. 고친 테스트가 수정 전 코드에서 실패하고 수정 후 통과하는지 확인한다.
3. 동작 코드가 바뀌면 [PR 검토 Skill](../review-pr/SKILL.md#결과)의 재검토 절차로 맡긴다. 테스트만 바뀌었으면 위 실패 확인으로 처리한다.

# 실행 중인 서비스 응답 확인

## 입력과 경계

- 서버 주소, 테스트 계정, `analysis/<대상>/extracted.json` 경로를 받는다. 테스트 환경에서만 쓴다.
- 넘겨받는 사람이 가진 것만 쓴다. `.env` 계열, 대상의 설정 값, 브로커·DB 직접 접근은 쓰지 않는다. 대상 코드는 요청을 만들거나 빠진 필드의 이유를 찾을 때만 읽는다.
- 토큰·비밀번호·계정 정보는 어떤 파일에도 남기지 않는다.

## 가정하는 구성

| 부분 | 가정 |
|---|---|
| 진입점 | 게이트웨이. 추출의 `externalPaths`로 호출 |
| 인증 | 테스트 계정으로 로그인해 받은 토큰 |
| 형식 | JSON 요청·응답 |

가정과 다른 부분은 추측하지 않고 호출하지 못한 이유로 남긴다.

## 1. 호출

1. 테스트 계정으로 로그인한다.
2. 조회 API 전부와 테스트 데이터로 부를 수 있는 쓰기 API를 부른다. 실제 결제·외부 발송처럼 테스트 범위 밖의 호출은 하지 않는다.
3. 엔드포인트마다 `analysis/<대상>/responses/<엔드포인트 ID>.json`에 저장한다. 부르지 못하면 `statusCode`와 `body`를 `null`로 두고 `reason`에 이유를 적는다.

   ```json
   {
     "request": {"method": "GET", "path": "/api/items", "body": null},
     "statusCode": 200,
     "body": {"message": "ok", "data": []},
     "reason": null
   }
   ```

## 2. 비교

```bash
python scripts/compare_responses.py analysis/<대상>/extracted.json analysis/<대상>/responses
```

엔드포인트별로 "응답에만 있음", "추출에만 있음", "이름 다름"을 출력한다. 오류 응답·빈 배열·`null`은 비교하지 않으므로, 데이터를 만들 수 있으면 다시 부른다.

## 3. 반영

- 응답에만 있는 필드는 더한다. Java 타입은 만들어 내지 않는다.
- 이름이 다른 필드는 `jsonName.value`를 실제 이름으로 바꾼다.
- 추출에만 있는 필드는 응답에 빠진 이유를 코드에서 찾는다. 조건부로 빠지면 그대로 둔다.
- 고친 사실의 근거는 `analysis/<대상>/responses/<엔드포인트 ID>.json:줄`(그 키가 있는 줄)로 바꾼다. `status`는 쓰지 않는다.
- 비교와 검증기를 다시 돌리고 호출한·못 한 엔드포인트 수, 차이 수(반영 전·후), 고친 수, 검사별 경고 수를 보고한다.

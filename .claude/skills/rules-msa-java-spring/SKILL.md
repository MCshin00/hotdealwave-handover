# 업무 규칙과 함정 기록

## 입력과 경계

- 대상 저장소 경로, 추출 결과 디렉터리(`analysis/<대상>`), 서비스의 애플리케이션 이름 목록을 받는다. 서비스마다 새 실행 문맥에서 이 Skill을 처음부터 따르고 파일 하나를 쓴다. 대상은 고정 커밋을 읽기만 하고 빌드하거나 실행하지 않는다.
- 이 Skill, [항목 형식](../../../docs/format/README.md)과 [항목 스키마](../../../docs/format/knowledge.schema.json), `out/analysis.json`의 추출 배열과 `warnings`, 지정한 추출 디렉터리의 서비스·관계 파일과 저장된 `responses/`, 대상 코드·설정만 읽는다. 형식 예시를 사실로 쓰지 않는다.
- `.env`, `.env.*`, `.local/`, `eval/`, 기존 `knowledge/` 결과는 읽지 않는다. `out/analysis.json`에 이미 항목이 있으면 `knowledge` 배열도 읽지 않는다.
- 코드와 JSON을 직접 읽고 항목을 직접 쓴다. 별도 모델 API, 추출 스크립트, 서버 재가동, 응답 재호출은 하지 않는다. 환경변수는 이름만 쓰고 비밀값·로컬 절대경로를 남기지 않는다.

## 1. 출발점 정하기

1. 추출된 서비스와 대상 설정의 `spring.application.name`을 대조해 서비스를 찾는다. 디렉터리 이름으로 애플리케이션 이름을 추정하지 않는다.
2. 이 서비스의 엔드포인트·Feign 호출·Kafka 발행·구독을 모두 출발점으로 삼는다. 요청 없이 실행되는 스케줄 작업도 더한다.
3. 이 서비스의 저장된 응답을 모두 읽고, 오류 응답, 호출하지 못한 이유(`reason`), 다음 호출에 쓸 값이 빠진 응답을 출발점에 더한다. `reason`은 코드를 따라갈 단서로만 쓴다.
4. 출발점의 처리 클래스가 빈으로 등록되는 근거를 코드에서 찾는다. 근거가 없으면 그 사실을 쓰고, 실제 실행 여부는 단정하지 않는다.

## 2. 처리 코드 읽기

출발점마다 처리 코드를 끝까지 따라가며 아래를 읽는다. 출력은 이 서비스 파일 하나지만, 동작을 설명하는 데 필요하면 호출하는 쪽·호출 대상·거치는 필터·같은 토픽의 발행·구독 코드도 읽는다. 게이트웨이·Feign·Kafka 절차는 대상에 그 구성이 있을 때만 따른다.

- 조건: 분기별 결과, 조회 조건과 반환 범위, 기본값
- 권한: 메서드의 역할 어노테이션과 코드 안의 역할·소유자 비교. 게이트웨이를 거치는 요청은 게이트웨이와 서비스 필터의 인증 제외 조건을 함께 본다.
- 예외: 예외가 나는 조건과 실제 응답 상태·오류 코드, 잡아서 삼키거나 정상으로 반환하는 곳
- 저장소 접근과 트랜잭션 경계, 실패할 때 앞선 변경이나 다른 서비스 호출을 되돌리는 처리
- 다른 서비스 호출: 응답을 만드는 쪽의 JSON 이름과 수신 클래스의 필드·setter·생성자·매핑 어노테이션을 대조하고, 받은 값을 이후 코드에서 어떻게 쓰는지 따라간다. 저장된 응답이 있으면 실제 JSON 이름과 값을 함께 본다.
- 주석: 의도를 읽되, 함수 이름과 주석은 코드로 확인한 동작과 대조할 뿐 그것만으로 동작을 단정하지 않는다.

## 3. 항목 고르기

읽은 것 중 아래에 해당하는 것만 항목으로 쓴다.

- `업무 규칙`: 추출 결과만으로는 알 수 없는 상태 전이, 계산, 입력 조건·중복·요청자 역할과 소유 검사, 조회 대상의 선택·제외 범위
- `함정`: 모르고 쓰면 잘못된 결과가 남거나, 원인과 다른 오류를 받거나, 필요한 작업이 막히는 동작. 쓰는 쪽은 API를 부르는 프론트·다른 서비스, 메시지를 주고받는 서비스, 서비스를 띄우고 운영하는 사람, 코드를 고치는 사람이다. 잘못 쓰는 상황은 코드나 응답으로 확인한 동작과 결과로만 쓰고, 일반적인 모범 사례나 바라는 동작에서 끌어내지 않는다. 실패했는데 성공으로 응답하거나 앞선 변경을 되돌리지 않는 것, 추출의 설정·환경변수를 모두 채워도 코드 때문에 막히는 준비를 포함한다.

업무 규칙과 함정에 모두 맞으면 함정으로 쓴다.

아래는 쓰지 않는다.

- 추출 결과의 값을 옮겨 적기만 하는 것. 추출된 사실끼리 비교하거나 처리 코드를 따라가야 드러나는 차이는 쓴다.
- 외부 자원이 필요하다는 사실만 있는 것
- `warnings`에 이미 나온 어긋남. 판정은 개발자가 한다.

같은 코드 원인에서 나오고 한 번 고치면 함께 해소되는 동작만 항목 하나로 묶는다. 여러 서비스에 걸친 동작은 원인 코드가 있는 서비스에 쓰고, 다른 서비스의 영향과 ID를 함께 넣는다.

## 4. 항목 작성

- `knowledge/<대상>/<spring.application.name>.json` 하나를 쓴다. `<대상>`은 입력 추출 디렉터리의 대상 이름이다. 형식은 `schemaVersion: 1`과 `items` 배열이며, 고른 항목이 없으면 빈 배열을 쓴다.
- 항목마다 `service`, `kind`, `title`, `description`, `evidence`, `affectedIds`, `source`, `discoveryPath`, `confirmationStatus`를 형식 문서대로 쓴다. 설명에는 코드나 저장된 응답으로 확인한 것만 쓰고, 확인하지 못한 실행 결과를 덧붙이지 않는다. 저장소 밖의 설정값이나 실제 연결을 추정하지 않는다.
- `source`는 `AI 해석`, `confirmationStatus`는 `미확인`으로 쓴다. 확인 상태는 개발자만 정한다. `판정` 출처를 만들지 않는다.
- `evidence`에 대상 루트 기준 `파일:줄`을 붙이고, 여러 파일에 걸친 동작은 연결되는 줄을 함께 넣는다. 줄 번호는 실제 파일에서 확인한다.
- 저장된 응답은 기록된 요청 조건에서 관찰한 상태 코드·본문의 근거로 쓴다. 응답을 근거로 쓰면 `analysis/<대상>/responses/<파일>.json:줄`을 붙이고 `discoveryPath`를 `실제 응답`으로, 코드 근거만 있으면 `코드`로 쓴다. 코드 해석과 응답이 어긋나면 차이를 쓰고 원인을 추정해 메우지 않는다.
- `affectedIds`에는 이 동작을 겪는 엔드포인트·Feign 호출·Kafka 발행·구독 ID만 넣는다. 추출 결과에 없는 ID를 만들지 않고, 붙일 ID가 없으면 항목으로 쓰지 않고 보고한다.

## 5. 저장 전 점검과 보고

- JSON 문법·스키마 필수 필드·허용 값, 근거 파일과 줄, 영향 ID의 존재를 점검한다. 설명이 맞는지는 개발자가 확인하며 검증기 통과가 개발자 확인을 대신하지 않는다.
- 결과 파일 위치, 출발점 ID마다 그 출발점에서 나온 항목 제목 또는 "없음", 따라가지 못한 경로, 3절 기준으로 뺀 것과 이유를 짧게 보고한다. 기존 항목·평가 자료와 대조하지 않는다.

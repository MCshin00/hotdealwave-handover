# PR 검토

## 먼저 볼 것

구현·수정에 참여했거나 그 대화나 요약을 전달받은 세션에서는 직접 검토하지 않는다. 그 대화를 이어받지 않은 새 세션(예: 새 `codex exec`)에 맡긴다. 이미 이 조건을 만족하는 리뷰 세션이면 아래 "근거"부터 진행한다.

- 맡기는 쪽은 저장소 위치, PR 번호와 이 Skill을 읽으라는 내용만 전달한다. 재검토면 이전 검토 커밋과 대상 커밋도 전달한다. 구현 설명·요약·검사 결과를 덧붙이지 않는다.
- 구현 세션을 리뷰어로 재사용하지 않는다.

## 근거

다음을 직접 읽고 근거로 쓴다.

- 이슈의 확인 조건과 댓글에 기록된 개발자 결정: `gh pr view N`에서 이슈 번호를 찾고 `gh issue view <이슈 번호> --comments`로 읽는다.
- PR 변경분: `gh pr diff N`. 대상 커밋 SHA는 `gh pr view N --json headRefOid`로 확인한다. 바뀐 파일은 필요하면 전체를 읽는다.
- 루트 [AGENTS.md](../../../AGENTS.md)와 [docs/decisions.md](../../../docs/decisions.md)의 관련 결정.
- 결과에 적힌 근거 `파일:줄`은 분석 대상 고정 커밋(`target/HotDealWave`)에서 직접 연다.
- 재검토에서는 이전 검토와 지적 처리 댓글도 읽고, 마지막 검토 커밋 이후의 변경분과 영향받는 코드·테스트로 판단한다.

PR 본문의 구현 설명과 구현한 쪽의 요약은 근거로 쓰지 않는다. 테스트 위치와 근거 링크는 원문을 찾는 데만 쓴다.

최종 질문(`eval/questions/final.csv`)은 열지 않는다. 새는지는 코드·설정·테스트가 그 경로를 읽거나 색인하는지로 판단한다.

## 검토

직접 실행하는 검사는 확인할 조건의 테스트로 한정한다. 전체 검사와 CI 결과는 PR에 남은 기록과 대상 커밋의 실행 기록을 근거로 쓴다.

1. 동작을 바꾸면 대표 테스트가 조건이 깨질 때 실패하는가. 문서·절차 변경은 조건별 대조 위치·방법·결과가 있는가.
2. 결과의 근거 `파일:줄`이 고정 커밋의 실제 줄과 맞는가. 표본을 골라 직접 연다.
3. 상태 표시 규칙을 지키는가. 이름이 비슷하다는 이유로 연결하거나, 저장소 밖 사실을 "확인됨"으로 내지 않는가.
4. 최종 질문이 코드·설정·테스트·색인에 들어가지 않았는가. 교차 검증 경고를 판정 없이 없애는 규칙 변경이 있지 않은가.
5. 로컬 절대경로나 비밀값이 커밋되지 않았는가. MCP·웹 입력으로 분석 범위 밖의 파일을 읽을 수 있지 않은가.
6. 대표 사례를 넘는 장치, 쓰이지 않는 추상화, 지울 수 있는 테스트가 있는가.
7. 이슈에 없이 스스로 정한 것이 있는가. 그것이 PR에 적혀 있는가.

조건을 어기는 경우를 찾는 것이 목적이다. 고정 커밋에 없는 입력에서만 재현되는 문제는 지적하지 않는다. 비밀값·로컬 경로 노출과 분석 범위 밖 파일 읽기는 지적한다.

## 결과

검토한 커밋 SHA를 적는다. 찾은 것마다 파일:줄, 어긴 조건, 깨지는 구체적인 경우를 쓴다. 없으면 "어긴 조건 없음"과 확인한 조건 목록을 쓴다. 판단하지 못한 확인 조건은 따로 적는다.

`gh pr comment N --body-file <파일>`로 PR에 댓글 하나로 남긴다. 파일을 고치지 않는다.

검토 뒤 동작 코드가 바뀌면 구현·수정에 참여하지 않은 새 세션이 위 "근거"의 재검토 범위로 다시 검토해 댓글을 남긴다. 테스트만 바뀐 수정은 [지적 처리](../work-issue/SKILL.md#지적-처리)의 실패 확인으로 처리한다.

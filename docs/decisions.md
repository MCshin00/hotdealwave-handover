# 결정 기록

개발자가 확정한 결정과 이유. 바뀐 결정은 해당 절을 고치고, 새 결정은 절을 더한다. 경로는 분석 대상(`target/HotDealWave`) 기준이다.

## 문제 상황

팀원이 모두 떠나고 배포도 멈춰, API·이벤트 흐름의 기록이 저장소에만 남은 마이크로서비스 프로젝트를 새 사람이 넘겨받아 다시 살린다. 새 사람은 API 스펙과 서비스 사이의 흐름을 매번 누군가에게 물어볼 수 없다. 저장소만으로 확인할 수 있는 것과 없는 것을 근거와 함께 보여 주는 도구를 만든다.

## 결과물 세 가지

| 결과물 | 쓰는 쪽 | 답을 만드는 모델 |
|---|---|---|
| 문서 페이지 | 사람이 읽음 | 없음 |
| 검색·질의응답 페이지 | 사람이 질문 | 서버가 호출(고정 RAG) |
| MCP | Claude Code·Codex | 클라이언트의 모델 |

세 결과물을 Spring Boot 서버 하나가 제공한다. 로컬에서도 같은 서버 하나를 띄우고, 배포할 때도 그 서버 하나를 올린다.

## 도구와 평가

도구는 대상 저장소마다 사람의 질문·채점 없이 돈다. AI 추출, 검증, 서버가 전부다. 검증 경고는 판정 없이 "확인 안 됨"으로 보여 준다.

평가는 이 도구가 실제로 돕는지를 HotDealWave에서 한 번 잰다([비교 실험](#비교-실험)). 두 번째 대상에는 질문·채점 없이 도구를 돌려 검증 경고와 깨진 곳만 본다.

## 구조

```
target/<대상> @고정 커밋 --> AI 추출(Skill) --> analysis/<대상>/extracted.json
                                                     |
                                                     v
                                    verifier --> out/analysis.json (상태·경고)
                                                     |
                                                     v
                                   server (Spring Boot, 하나의 프로세스)
                                     +-- 조회: 관계 조회 3개 + 검색(BM25)
                                     +-- 페이지: 문서·검색·질문 (Thymeleaf)
                                     +-- /api/search, /api/ask
                                     +-- /mcp  <-- Claude Code·Codex (HTTP)
```

- `verifier`와 `server`는 같은 Gradle 프로젝트의 모듈이고, `out/analysis.json` 하나로만 연결한다. 스키마는 양쪽 테스트가 확인한다.
- 조회 계층은 관계 조회 3개(`find_endpoint`, `trace_flow`, `find_subscribers`)와 `search_docs`(BM25)를 제공하고 모델을 부르지 않는다. 페이지, API, MCP가 모두 이 계층을 쓴다.
- `/mcp`는 조회 계층을 MCP 도구로 그대로 노출한다(Streamable HTTP). 답은 클라이언트의 모델이 쓴다. 서버 안에서 모델을 부르는 도구는 두지 않는다.
- `/api/ask`는 고정 RAG다. 항상 `search_docs`로 찾고, 모델을 한 번 부르고, 인용을 검사해 답하거나 보류한다. 질문당 호출 수가 정해져 있어 비용을 미리 말할 수 있고, 같은 질문으로 다시 재기 쉽다. 흐름을 여러 단계로 따라가는 질문은 MCP 경로가 맡는다.
- 답은 인용 검사를 통과한 뒤 한 번에 보여 준다. 스트리밍은 하지 않는다. 화면에 먼저 나간 답은 검사할 수 없기 때문이다.
- 질문은 하나씩 받는다. 대화 기록을 넘기면 "그럼 결제는?" 같은 후속 질문에서 검색이 빗나가고, 채점도 질문 단위로 해야 하기 때문이다.

## 검색

- 조각은 문서 페이지를 엔드포인트·토픽·서비스 단위로 자른 것이다.
- 질문에 서비스 이름(주문, 상품, 결제 등)이나 종류(API, 토픽, 설정 등)가 나오면 그 서비스·종류의 조각만 먼저 찾는다. 결과가 없으면 필터를 하나씩 풀어 다시 찾는다. 서비스·종류 목록은 `analysis.json`에서 가져온다.
- 같은 페이지의 조각은 점수가 가장 높은 하나만 남기고 상위 5개를 고른다.
- 토큰화는 식별자를 통째로, camelCase·snake_case 단위로도 나누고, 한국어는 두 글자씩 자른다.
- 임베딩은 채점에서 BM25가 표현 차이로 근거를 놓치는 경우가 확인될 때만 더한다.

## 언어와 라이브러리

| 부분 | 선택 | 이유 |
|---|---|---|
| 추출 | AI 세션(Claude Code·Codex)과 Skill | 프레임워크가 달라도 지시문으로 따라간다. 세션 작업이라 별도 유료 호출이 없다 |
| 검증 | Java 17, SnakeYAML, Jackson | 서버와 같은 실행 환경이다. 확인 상태는 AI가 아니라 검증이 정한다 |
| 기준선 | Java 17, JavaParser 3.28.2(JavaSymbolSolver 포함) | HotDealWave에서 AI 추출 결과를 대조한다 |
| 서버 | Spring Boot, Thymeleaf, Mermaid(흐름 그림) | 검증과 같은 실행 환경 하나로 빌드·테스트·배포한다. 개발자가 직접 읽고 판단할 수 있는 스택이다. 화면 모양은 중요하지 않다 |
| MCP | MCP Java SDK(`mcp-core`의 서블릿용 Streamable HTTP 전송) | Spring Boot에 바로 붙는다. Claude Code·Codex 모두 HTTP 방식 MCP를 등록할 수 있어 표준 입출력 방식은 두지 않는다 |
| 질의응답 | OpenAI Java SDK(정해진 형식의 출력) | rag-chatbot의 방식(BM25, 정해진 형식의 답·인용·보류, 보류 규칙)을 옮긴다. 인용 검사는 답의 `파일:줄`이 인용한 조각에 있는지까지 본다. 모델은 질의응답 단계에서 비용과 함께 정한다 |

## 배포

배포는 선택이다. 하게 되면 서버 하나를 손으로 올리고 CD는 붙이지 않는다. `out/analysis.json`은 이미지를 만들 때 넣는다. `/api/ask`는 하루 호출 상한을 두고, 모델 키는 배포처의 비밀값으로 둔다. 원격 `/mcp`는 공개 저장소를 분석한 읽기 전용 데이터라 인증 없이 연다.

## 분석 대상: 원본 저장소의 `cc43016`

팀 원본 저장소(`sparta-final-12th-9700/HotDealWave`)의 main 끝 커밋(2025-01-24)이다. 새로 온 사람이 받는 것은 팀 원본이므로 그 상태를 그대로 분석한다. 원본에 접근할 수 없게 되면 같은 커밋을 가진 포크로 `.gitmodules`의 주소만 바꾼다.

두 번째 대상은 개발자의 공개 저장소 하나다. 커밋을 고정하고 같은 도구를 돌려, 다른 저장소에서 어디까지 되는지 본다.

## 추출 방식

AI 세션이 Skill을 따라 대상 코드를 읽고 정해진 형식으로 쓴다. 항목마다 근거 `파일:줄`을 붙인다. 결과는 다시 만들 수 없어 `analysis/<대상>/`에 커밋한다.

파서 추출기(`extractor/`)는 HotDealWave의 기준선이다. AI 추출 결과와 항목별로 대조해 일치율과 틀린 곳을 낸다. 파서로 만든 규칙은 대상 저장소의 코드 모양에 묶여 다른 저장소에 쓸 수 없었다.

## Kafka 연결 규칙

토픽 이름은 코드와 설정 어디에도 값으로 없다. `@Value("${spring.kafka.topics.x}")` → `application.yml`의 `${KAFKA_..._TOPIC}` → `docker-compose.yml`의 `${KAFKA_..._TOPIC}`으로 이어지고, 값은 배포 서버의 환경에서 들어온다(`.github/workflows/actions.yml`이 EC2에서 `docker-compose`를 실행).

- 발행 쪽과 구독 쪽이 같은 환경변수 이름을 쓰면 연결한다. 한 compose 파일 안의 같은 `${변수}`는 같은 값으로 채워지기 때문이다. 근거는 양쪽 서비스의 compose 줄이다.
- 이름이 다르면 "확인 안 됨"으로 둔다. 이름·필드명·로그 문구가 비슷해도 후보로 내지 않는다.
- 실제 값은 쓰지 않는다. 저장소만 받은 사람은 그 값을 알 수 없다.

## 따라가는 범위

추출이 따라가야 하는 HotDealWave의 패턴이다. 사슬의 줄마다 근거를 붙이고, 근거가 끊긴 값은 "확인 안 됨"이다.

| 패턴 | 예 |
|---|---|
| private 래퍼 | `order/.../OrderEventProducer.java:37` → `:62`의 `kafkaTemplate.send` |
| 토픽이 인자로 여러 번 전달됨 | `product/.../ProductKafkaConsumer.java:48` → `:85` → `ProductInventoryService.java:125` → `ProductKafkaProducer.java:14` |
| `send` 없는 DLQ 발행 | `order/.../ConsumerApplicationKafkaConfig.java:61`의 `DeadLetterPublishingRecoverer` |
| 게이트웨이 경로 | `gateway/src/main/resources/application.yml`의 `lb://` 경로 규칙 |
| Feign `name` → 대상 서비스 컨트롤러 | `order/.../ProductClient.java:26`(메서드 `reduceQuantity`, 경로 `/restore-quantity`) |
| 코드에 박힌 외부 URL | `payment/.../KakaoPayClient.java:14` |

## 설정과 외부 자원

서비스를 다시 띄우는 데 필요한 것을 뽑는다. 서비스마다 쓰는 환경변수 이름, 외부 자원(DB, Redis, Elasticsearch, Kafka, S3, KakaoPay)과 그것을 쓰는 코드·설정의 `파일:줄`이다. 환경변수 값과 버킷 이름은 "저장소에 근거 없음"이다.

## API 요청·응답

엔드포인트마다 HTTP 메서드와 전체 경로, 파라미터 종류(경로·쿼리·본문), 요청·응답 DTO의 필드 목록과 클래스 위치까지 뽑는다. API 스펙을 묻는 질문에 필드로 답해야 하기 때문이다.

프론트 개발자가 API를 붙일 때 필요한 것도 함께 뽑는다. 게이트웨이 기준 외부 경로, 필드의 검증 어노테이션(`@NotNull` 등), 필드의 실제 JSON 이름, 게이트웨이에서 토큰이 필요한지(HotDealWave는 `gateway/.../filter/AllowedPath.java`)다. Swagger는 서비스를 띄워야 보이고 설명도 거의 없다.

## 검증

사람이 미리 정답표를 쓰지 않는다. 넘겨받는 사람도 구조를 다 알지 못한 채 시작하기 때문이다. 대신 추출 결과를 대상 저장소의 코드 자체와 비교해, 어긋나는 곳을 경고로 낸다.

| 검증 | 보는 것 | 어긋나면 |
|---|---|---|
| 근거 줄 | 근거 `파일:줄`이 고정 커밋에 있고, 그 줄에 항목의 경로·토픽·필드 이름이 있는가 | 그 항목은 "확인 안 됨" |
| 선언 목록 | 정규식으로 센 선언(`@*Mapping`, `@FeignClient`, `@KafkaListener`, `send`) ↔ 추출 항목 | 빠뜨린 선언 경고 |
| 관계 | 호출 대상 엔드포인트, 발행↔구독 환경변수 이름, 게이트웨이 경로가 결과 안에서 맞는가 | 끊긴 관계 경고 |

세 검증을 통과한 항목만 "확인됨"이다. 값이 `${ENV}`로만 나오는 항목은 "저장소에 근거 없음"이다. 선언 패턴은 프레임워크별로 두고, 지금은 Spring 하나다.

경고 판정은 선택이다. 4단계에서 함정을 확인할 때 필요한 경고만 판정해 `eval/facts.csv`에 남긴다. 형식은 [eval/README.md](../eval/README.md). 경고를 없애려고 Skill이나 검증 규칙을 바꾸지 않는다.

## 업무 규칙과 함정

추출은 관계만 뽑는다. 넘겨받는 사람이 실제로 많이 부딪히는 상태 전이, 계산, 검증 규칙과 겉으로 드러나지 않는 동작은 뽑지 못한다. 그래서 이 내용을 담는 층을 하나 더 둔다.

- 출처는 둘이다. 하나는 AI가 `analysis.json`의 사실을 출발점으로 서비스 코드를 읽고 쓴 항목이고(Codex 세션 작업, 별도 유료 호출 없음), 다른 하나는 경고 판정에서 "코드의 실제 어긋남"이 된 항목이다.
- 항목마다 서비스, 제목, 설명, 근거 `파일:줄`, 출처(AI 해석·판정), 확인 상태(확인함·틀림·미확인)를 둔다.
- AI 해석 항목은 개발자가 근거를 열어 확인하기 전까지 "미확인"이고, 페이지에도 그렇게 표시한다. "틀림"이 된 항목은 내보내지 않는다.
- 다시 만들 수 없는 결과라 `knowledge/`에 커밋한다. 문서 페이지와 `search_docs` 색인에 들어간다.

## 비교 실험

"기본 코드 검색만"과 "MCP 도구 추가"를 같은 모델·커밋·질문·예산으로 비교한다. 조건마다 새 대화로 시작하고, 이 저장소가 없는 원본 저장소의 깨끗한 체크아웃(`cc43016`)에서 실행한다.

질문은 개발자가 지금 실제로 궁금한 것으로 쓰고(`eval/questions/final.csv`), 도구 결과를 보기 전에 고정한다. 답에는 근거 `파일:줄`을 붙이게 하고, 개발자가 근거를 열어 채점한다. 정확도, 걸린 시간, 비용, 풀지 못한 질문을 기록한다.

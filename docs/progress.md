## 지금 위치

4단계 완료(#13). 엔드포인트 72개 중 61개를 불러 응답을 저장했고(정상 56, 오류 5), 11개는 이유와 함께 남겼다. 정상 응답의 필드 차이는 0개여서 서비스 파일 수정은 없다. 검증 경고는 12개(선언 목록 1, Kafka 발행↔구독 11)다. 3단계 뒤 바뀐 구조(#15·#18·#19)와 4단계 결과는 [4단계 보고서](reports/probe-hotdealwave.md)에 있다.

5단계 완료. #21에서 항목 형식·검증기 검사·`rules-msa-java-spring` Skill을 만들고 7개 서비스에 AI 해석 항목 124개를 썼다. DLQ 경고 2개는 판정해 판정 항목 1개로 옮겼다. #23에서 서비스별 결과를 한 번에 읽는 정리 단계를 더해 서비스 사이 중복을 합치고 덧말을 지웠다(항목 127개, AI 해석 126개는 미확인). `reduceQuantity` 함정 분리와 관리자 주문 상태 수정의 분류는 놓친 채 기록했다. #22에서 검증기가 주석 속 선언을 세지 않게 했다. 검증 경고는 `kafka-topics` 11개만 남았다. 결과와 Skill을 고친 과정은 [5단계 보고서](reports/rules-hotdealwave.md)에 있다. 다음 할 일: 6단계.

6단계 완료. #30에서 엔드포인트·Kafka 구독이 같은 서비스의 Feign 호출·발행에 닿는 연결(`calls`) 42개를 관계 파일에 더하고 검증기가 확인하게 했다(`handler-calls` 경고 2개: 부르는 곳 없는 Feign 호출). 2026-11-04 순서를 조정했다. 새 검증 규칙과 페이지 꾸미기보다 검색·MCP를 먼저 하고, 6단계 본문은 텍스트로 값·상태·근거까지만 보여 준다. #28에서 `server` 모듈을 더했다. 조회 계층은 `out/analysis.json`만 읽어 엔드포인트 찾기, 호출·발행·구독 따라가기(이어지지 않는 발행은 "확인 안 됨"과 경고 이유에서 멈춤), 토픽의 발행·구독 찾기를 한다. 엔드포인트·토픽·서비스 본문은 값마다 상태와 근거 `파일:줄`을 붙이고, 확인되지 않은 값은 상태와 이유를 대신 보여 주며, 관련 업무 규칙·함정을 함정 먼저 붙인다. 다음 할 일: 7단계.

7단계 완료. #33에서 본문을 `h2` 절 조각으로 색인하는 `search_docs`(BM25)와 `/api/search`, 도구 5개(`find_endpoint`, `trace_flow`, `find_subscribers`, `search_docs`, `get_page`)를 여는 `/mcp`를 더했다. Codex와 Claude Code에서 질문 하나씩으로 도구가 불리고, `requestProduct` 뒤의 "확인 안 됨"과 근거 `파일:줄`이 답에 그대로 전달되는 것을 확인했다. 다음 할 일: 8단계.

8단계 완료. #35에서 `/api/ask`(검색 상위 5개 → `gpt-6-luna` 한 번 → 인용 검사로 답·보류)와 검색·질문 페이지 `/search`를 더했다. 실제 호출 4번에서 필드 질문은 근거와 함께 답했고, 저장소에 없는 값은 보류했으며, `requestProduct` 수신자는 "확인 안 됨"으로 답했다. 남은 문제는 둘이다. 본문의 한국어가 AI 해석 항목에만 있어, 한국어로 물으면 코드 이름뿐인 흐름 절이 검색되지 않는다. 어노테이션이 없는 필드는 빈칸이라 모델이 다른 줄을 따라 지어낸다(추론 low·medium도 같음). #37에서 빈 필드를 "어노테이션 없음"으로 쓰고, 항목 종류 `설명`을 더해 업무 규칙 Skill이 엔드포인트·Kafka 발행·구독 94개에 한국어 설명을 썼다(AI 해석, 미확인). 설명은 페이지 맨 위 "설명" 절에 나오고, 모델에는 엔드포인트와 함께 토픽 페이지도 본문 전체를 넘긴다. Kafka 연결 경고의 이유는 식별자 나열에서 "같은 환경변수를 쓰는 구독을 찾지 못함, 토픽 값은 저장소 밖에서 정해짐" 문장으로 바꿨다. 실제 호출에서 couponId는 "검증 어노테이션 없음"으로, `requestProduct` 수신자는 "확인 안 됨"과 그 이유로 답했다(입력 1만에서 2만 토큰). #39에서 페이지를 꾸몄다. 근거 `파일:줄`은 접어 두고 고정 커밋 원본 줄·응답 원문 페이지로 링크하며, 흐름 단계는 상자·화살표로 잇고, 줄과 항목을 상태(확인됨·확인 안 됨·저장소에 근거 없음·AI 해석)별 색으로 가른다. 그림 라이브러리는 쓰지 않고, 검색·MCP·모델이 읽는 본문 글자는 꾸미기 전과 같다(전체 724개 절 대조). 6~8단계의 결과와 실제 호출·비용은 [서버 보고서](reports/server-hotdealwave.md)에 있다. 다음 할 일: 9단계.

9단계 진행 중. #41에서 실행 스크립트와 기계 검사를 만들고, 저장소 체크아웃에 MCP를 더한 조건으로 연습·최종 질문을 돌렸다. 결과를 보고 문제 상황을 "서비스가 떠 있고 문서가 없음"과 "저장소만 남음"으로 나눴다. 저장소가 있으면 분석용 MCP는 이득이 없어, MCP 조건을 저장소 없이 다시 정했다(#43).

9단계 완료. #43에서 MCP 조건을 원본 코드가 없는 작업 폴더로 다시 돌렸다. #45에서 Codex·Opus 교차 채점을 하고, 갈린 칸은 개발자가 정한 기준으로 판정했다(개발자 3칸, Opus 판정·Codex 반박·Opus 최종 24칸). 최종 질문 21개에서 기준선은 모두 맞음, MCP는 맞음 12·부분 9·틀림 0, 질의응답은 맞음 6·부분 11·틀림 4였다. MCP는 확인 안 된 것을 확인된 것처럼 말한 답이 없었고, 질의응답은 1개(Q01)였다. 맞음이 아닌 답 24개 가운데 13개는 문서에 그 내용이 없어서이고, 배포 워크플로·오류 응답 본문·페이지 직렬화 설정처럼 아직 추출하지 않은 것에 몰렸다. 질의응답은 검색에서 못 찾은 경우가 5개다. 다루는 범위는 근거 위치로 가르기로 했다. 결과와 원인은 [9단계 보고서](reports/eval-hotdealwave.md)에 있다. 다음 할 일: 추출 범위(배포 워크플로, 오류 응답 본문, 페이지 직렬화 설정, 모니터링 설정)와 질의응답 검색을 고친 뒤 10단계.

9단계 뒤 개선 완료. 9단계에서 문서에 없어 맞음이 되지 못한 내용을 추출 범위에 더했다. #47에서 오류 코드, 예외 처리기, Gateway 거부 응답, 페이지 직렬화 설정을 서비스 파일에, 엔드포인트에서 예외 생성 줄까지의 연결(`throws`)을 관계 파일에 더했다. 처리기 안에서 조건에 따라 값이 갈리면 "확인 안 됨"이다. #49에서 서비스 하나에 속하지 않는 배포 워크플로, 컨테이너 이미지, 메트릭 수집, 로그 전송, 모니터링 도구 설정을 `repository.json`과 `/repository` 페이지로 냈다. Secrets 값과 실행 환경 값, 모니터링 도구의 실행 정의는 "저장소에 근거 없음"이다. #51에서 이 형식을 도구 이름이 아닌 역할(배포 파이프라인, 컨테이너, 메트릭 수집, 로그 전송, 도구 자체 설정, 모니터링 도구)로 나눠, 다른 저장소의 도구도 같은 칸에 담게 했다. #53에서 질의응답 검색을 조정용 질문 8개(T03~T10, AI 초안을 최종 질문과 겹치지 않게 거른 뒤 개발자가 확정)로 조사했다. "받은 문서에서 빠뜨림"은 재현되지 않았다. 원인은 문서 용어 연결(핫딜 ↔ 타임세일), BM25의 표현 차이(HTTP 호출 ↔ Feign), 질문에 섞인 낱말로 좁혀지는 종류 거르기였다. 지시문 수정과 종류 말 수정은 효과가 없거나 다른 질문을 나쁘게 해 채택하지 않았다. 남긴 문제는 #53 댓글에 있다. 다음 할 일: 10단계. 시작할 때 대상의 통신 방식·기술을 도구 지원 범위와 대조하고, 서버에 고정된 대상 이름과 루트 `docker-compose.yml` 전제를 확인한다. 질의응답이 어디서 놓치는지 볼지(결정 기록은 두 번째 대상에 질문·채점을 하지 않는다)도 그때 정한다.

10단계 준비 중. #55에서 서버가 대상 이름·고정 커밋·근거 링크 주소를 분석 데이터(`target.json`)에서 읽게 했다. 두 번째 대상을 처음 쓰는 사람의 순서로 쓰도록 점검해 고칠 곳을 찾았다. 대상을 서브모듈 대신 작업 폴더로 받고, 서버가 대상마다 따로 뜨게 하는 것 등이다. 두 모델의 독립 설계안, 교차 비판, 별도 판정을 거쳐 [사용 범위와 흐름](decisions.md#사용-범위와-흐름)를 정했다. #56에서 대상을 작업 폴더로 떼어 냈다. `init`이 대상을 작업 폴더에 복제해 커밋을 고정하고 AI 세션용 지시 파일을 쓰며, AI가 `verify`로 검증 출력을 만들고 사람이 `serve`로 띄운다. HotDealWave는 결과와 검증 출력을 커밋한 예시 작업 폴더(`examples/hotdealwave`)가 됐고, 옮기기 전후 페이지 본문은 응답 근거 경로 말고 같다. #58에서 형식을 바꾸지 않고 흔한 Spring MSA 구성을 읽게 했다. 하위 폴더의 Maven·Kotlin DSL 모듈, `properties`·`yaml` 설정, 위치가 다른 compose 파일과 맵 형식 `environment`, 기본값 있는 환경변수, 같은 토픽 이름의 Kafka 연결, Java DSL 경로와 `StripPrefix`, Spring Security `permitAll`, record와 `@JsonProperty`다. 필드의 `@JsonProperty`·`@JsonNaming`을 무시하고 getter 이름을 "확인됨"으로 내던 문제와, 앞부분 일치가 아닌 인증 필터에서도 토큰 판정을 "확인됨"으로 내던 문제를 함께 고쳤다. HotDealWave 예시의 검증 출력은 그대로다. 다음 할 일: 경고 이유 코드·표시·`unsupported` → SpartaHub 시험 → 질의응답 하이브리드 검색 → 되살리기 페이지.

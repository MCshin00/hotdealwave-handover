# 업무 규칙·함정 보고서: HotDealWave

이슈 #21(5단계)의 결과다. 추출 결과(엔드포인트·Feign·Kafka)에서 출발해 서비스 코드와 저장된 응답을 읽고, 넘겨받는 사람이 추출만으로는 알 수 없는 업무 규칙과 함정을 항목으로 남겼다. 업무 규칙 Skill로 7개 서비스에서 AI 해석 항목 124개를 썼고, 경고 판정 2건을 판정 항목 1개로 옮겼다. 검증기의 항목 경고는 0개다. Skill은 두 번 고쳐 세 번 실행했고, 마지막 결과의 표본 13개는 AI 두 곳이 따로 확인해 모두 코드와 맞았다.

## 1. 구성

| 부분 | 위치 | 하는 것 |
|---|---|---|
| 항목 형식 | [docs/format/knowledge.schema.json](../format/knowledge.schema.json), [형식 문서](../format/README.md) | 서비스, 종류(업무 규칙·함정), 제목, 설명, 근거 `파일:줄`, 영향 ID, 출처(AI 해석·판정), 발견 경로(코드·실제 응답), 확인 상태(확인함·틀림·미확인) |
| 검증기 검사 | `verifier/` | 항목 파일을 스키마로 검사하고, 근거 줄이 고정 커밋이나 응답 파일에 있는지(`knowledge-evidence`), 영향 ID가 추출 결과에 있는지(`knowledge-affected-ids`) 본다. 항목을 `out/analysis.json`의 `knowledge` 배열에 합치고 "틀림"은 넣지 않는다 |
| Skill | [rules-msa-java-spring](../../.claude/skills/rules-msa-java-spring/SKILL.md) | 서비스마다 새 실행 문맥에서 출발점 정하기 → 처리 코드 읽기 → 항목 고르기 → 작성 |
| 경고 판정 | `eval/facts.csv` | 함정 확인에 필요한 경고를 개발자가 판정하고, "코드의 실제 어긋남"을 판정 항목으로 옮긴다 |

```
out/analysis.json(추출) + analysis/hotdealwave/responses/ + target/HotDealWave @cc43016
  --> 업무 규칙 Skill(서비스마다 한 번) --> knowledge/hotdealwave/<서비스>.json
  --> 경고 판정(개발자) --> eval/facts.csv --> 판정 항목
  --> verifier --> out/analysis.json의 knowledge 배열
```

## 3. Skill을 고친 과정

대조 기준은 이슈 #21에 적은 후보다. 후보는 4단계 응답 확인과 코드 검토에서 나온 것이며 결과 파일에 직접 더하지 않았다.

| 실행 | Skill | 실행 방식 | 항목(규칙/함정) |
|---|---|---|---:|
| 1회차 | 처음 Skill(읽을 것 목록만 있음) | 한 세션에 8개 서비스 | 41 (15/26) |
| 2회차 | 1회차에서 놓친 원인마다 읽을 것 문장 4개 추가 | 한 세션에 8개 서비스 | 63 (17/46) |
| 3회차 | 출발점·읽기·고르기·작성으로 개편 | 서비스마다 새 세션 7번 | 124 (61/63) |

| 후보 | 1회차 | 2회차 | 3회차 |
|---|---|---|---|
| 쿠폰 검증 응답의 `valid`를 주문 쪽 수신 클래스(`isValid`, setter 없음)가 받지 못해 쿠폰을 사용 처리하지 않음 | 반대로 해석 | 찾음 | 찾음 |
| 게이트웨이는 리뷰 GET을 인증 없이 통과시키지만 상품 서비스 필터는 사용자 헤더를 요구함 | 놓침 | 찾음 | 찾음(gateway·product에 중복) |
| DLQ 구독 클래스에 빈 등록 어노테이션이 없음 | 놓침 | 찾음 | 찾음 |
| order의 Feign 메서드 `reduceQuantity`가 재고 복구 API를 부름 | 찾음 | 찾음 | 주문 취소 업무 규칙 설명 안에 한 문장으로만 남음 |
| 서비스를 다시 띄울 때 막히는 곳 6가지 | 2 | 5 | 3 |

- DLQ 발행 문자열이 서로 다른 후보는 경고 판정으로 다룬다(5절).
- 막히는 곳 3회차: 이메일 인증 필요, 일반 가입으로 관리자를 만들 수 없음, 업체 생성·조회 응답에 업체 ID가 없음(세 실행 중 처음). 외부 결제 필요는 고르기 기준(외부 자원이 필요하다는 사실만 있는 것은 쓰지 않음)으로 뺐다. S3 접속 주소를 바꿀 수 없음과 검색 색인 매핑은 놓쳤다.

**1회차 → 2회차.** 놓친 원인은 Codex 실행 기록으로 찾았다. Codex는 관련 파일을 열었지만 무엇을 봐야 하는지 몰라 지나쳤다. 쿠폰은 응답 쪽 JSON 이름 규칙(getter 기준)을 수신 쪽에도 적용해 이름이 맞는다고 봤다. 그래서 수신 클래스, 처리 클래스의 빈 등록, 게이트웨이와 서비스 필터, 실행 준비를 읽으라는 문장을 더했다. 후보는 대부분 찾았지만 "업체 저장에는 MySQL과 스키마 준비가 필요하다"처럼 추출 결과에 이미 있는 사소한 항목이 늘었고, 1회차에 있던 항목 5개가 빠졌다.

**2회차 → 3회차.** 원인은 Skill이 읽을 것만 정하고 무엇을 항목으로 쓸지 고르는 기준이 없었던 데 있었다. 개편안은 Codex와 Opus 리뷰 에이전트가 따로 검토했다. 바꾼 것은 다음과 같다.

- 출발점에 스케줄 작업과 저장된 응답(오류 응답, 호출하지 못한 이유, 다음 호출에 쓸 값이 빠진 응답)을 더했다.
- 고르기 기준을 따로 두었다. 업무 규칙은 추출만으로 알 수 없는 상태 전이·계산·검증·권한·조회 범위로, 함정은 이름·주석·요청과 응답 형식·호출하는 쪽 코드에 근거한 기대와 실제 동작이 다른 것으로 정했다. 추출 값을 옮겨 적기만 하는 것, 외부 자원이 필요하다는 사실만 있는 것, 검증 경고에 이미 나온 어긋남은 쓰지 않는다.
- 2회차에 넣은 수신 클래스 문장("getter로만 생기는 이름은 받지 못한다")은 일반적으로 맞지 않아, 응답 JSON 이름과 수신 클래스의 필드·setter·생성자·매핑 어노테이션을 대조하는 문장으로 바꿨다.
- 서비스마다 새 실행 문맥에서 실행한다.

3회차에서 사소한 항목과 경고와 겹치는 항목은 사라졌고, 2회차에 빠졌던 1회차 항목 5개가 모두 다시 나왔다.

수신 클래스, 빈 등록, 게이트웨이 필터를 읽으라는 문장은 놓친 후보를 보고 넣었다. 그래서 2·3회차의 후보 수치는 같은 후보로 다시 잰 것이며, 처음 보는 저장소에서의 성능을 뜻하지 않는다. 일반화는 10단계 대상에서 확인한다.

## 4. 정확도(AI 교차 확인 잠정치)

3회차 124개에서 서비스와 종류 조합마다 하나씩, 고정 시드로 무작위로 13개를 뽑았다(gateway는 함정만 있어 하나). Codex와 Opus 리뷰 에이전트가 항목의 근거 줄을 쓰지 않고 코드를 따로 따라가 확인했다.

## 5. 경고 판정

| id | 경고 | 판정 | 실제 연결 | 근거 |
|---|---|---|---|---|
| F1 | `kafka-topics`: 구독자 확인 안 됨(`payment-dlq`) | 코드의 실제 어긋남 | 아니오 | 코드 확인 |
| F2 | `kafka-topics`: 구독자 확인 안 됨(`product-dlq`) | 코드의 실제 어긋남 | 아니오 | 코드 확인 |

payment와 product는 처리에 실패한 메시지를 각각 문자열 토픽 `payment-dlq`, `product-dlq`로 보낸다(`ConsumerApplicationKafkaConfig.java:61`). DLQ 구독 클래스 `OrderDlqConsumer`·`PaymentDlqConsumer`는 환경변수 `KAFKA_DLQ_TOPIC` 하나를 구독하도록 선언됐지만 빈 등록 어노테이션이 없고, 다른 곳에서 등록하는 코드도 없어 구독이 시작되지 않는다. 두 판정을 판정 항목 하나("문자열로 지정한 DLQ 토픽 두 개를 받는 쪽이 없다", payment-service, 확인함)로 옮겼다.

선언 목록 경고(`PaymentViewController.java:12`, 블록 주석 안의 `@GetMapping`)는 판정하지 않았다. 주석 속 선언은 등록되지 않으므로 검사가 세지 않는 것이 맞다고 보고, 검사를 고치는 일을 #22로 냈다. 나머지 `kafka-topics` 경고 9개는 함정 확인에 필요하지 않아 판정하지 않았다.

## 6. 남은 문제

| 문제 | 예 | 처리 |
|---|---|---|
| 같은 문제가 두 서비스 결과에 따로 있다 | 리뷰 조회 인증 차이(gateway·product), 승인 안 된 업체의 상품 등록(company·product). 서비스마다 따로 실행해 다른 결과를 모르고, 원인이 두 서비스에 걸치면 어느 쪽에 쓸지 정해 두지 않았다 | [#23](https://github.com/MCshin00/hotdealwave-handover/issues/23) |
| 원인이 다른 내용이 한 항목에 섞였다 | `reduceQuantity` 함정이 주문 취소 업무 규칙 설명 속 한 문장으로만 남았다 | #23 |
| 설명에 AI가 자기 작업을 밝힌 말이 섞였다 | "실제 실행 결과는 확인하지 않았다", Skill 문장을 옮긴 "추정하지 않는다". 같은 표현이지만 필요한 정보인 문장(코드가 확인하지 않는다는 서술, 인용한 응답이 보여 주는 범위)도 있어 표현으로는 가를 수 없다 | #23 |
| 검사·부수 처리가 없다는 서술의 분류가 흐리다 | 업체 등록 상태를 요청값으로 저장, 관리자 주문 상태 수정에 부수 처리 없음이 업무 규칙으로 들어갔다 | #23에서 대조 기준으로 결과를 본다 |
| 같은 모양의 항목이 서비스마다 반복된다 | Kafka 전송 완료를 확인하지 않음(order·payment·product), 수동 확인 모드에서 확인 호출 없음(order·payment) | 서비스마다 원인 코드가 따로 있어 합치지 않는다 |
| 근거 줄이 많다 | 항목당 4~42줄, 중앙값 13줄. 판단에 결정적이지 않은 줄이 섞인다 | 페이지에 보여 줄 줄 수를 6단계에서 정한다 |

#23은 6단계 전에 처리한다. 중복은 검증기가 영향 ID로 찾고(서비스가 다른 항목끼리 영향 ID 목록이 같은 쌍은 위 두 쌍뿐이다), 나머지는 Skill 문장 두 개와 서비스별 결과를 한 번에 읽는 정리 단계로 고친다. 주석 속 선언은 #22에서 고친다. 빈 등록이 없는 Kafka 수신 클래스와 Feign 수신 이름 불일치를 코드로 찾는 검사는 하지 않고, 10단계에서 놓치면 다룬다.

## 7. 한계

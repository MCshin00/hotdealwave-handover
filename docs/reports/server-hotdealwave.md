# 서버 보고서: 문서 본문, 검색·MCP, 질의응답·페이지

6~8단계의 결과다. 세 단계는 `server` 모듈 하나를 쌓았고, 모두 같은 본문을 쓴다. 6단계에서 엔드포인트·토픽·서비스 본문을 만들었고, 7단계는 그 본문을 절 조각으로 잘라 검색과 MCP에 넘겼으며, 8단계는 같은 본문을 모델에 넘기고 사람에게는 꾸며서 보여 준다. 단계는 본문을 읽는 쪽(사람, 에이전트, 모델·브라우저)으로 나눴다.

## 1. 구성

```
out/analysis.json (검증기 출력: 추출·연결·응답 확인·항목·경고)
  --> Queries (관계 조회 3개)                                         6단계
  --> Pages: 같은 템플릿으로 엔드포인트·토픽·서비스 본문 렌더링       6단계
        +-- h2 절 조각 724개 --> Search (BM25) --> /api/search        7단계
        |                                      --> /mcp 도구 5개      7단계
        |                                      --> /api/ask           8단계
        +-- Decor (브라우저에 보낼 때만 덧씌움) --> 문서 페이지        8단계
```

| 부분 | 파일 | 하는 것 |
|---|---|---|
| 데이터 | `Analysis` | `out/analysis.json`만 읽는다. 서버는 저장소나 분석 대상 파일을 열지 않는다 |
| 조회 | `Queries` | `find_endpoint`, `trace_flow`, `find_subscribers`. 모델을 부르지 않는다 |
| 본문 | `Pages`, `View`, 템플릿 | 값마다 확인 상태와 근거 `파일:줄`, 확인 안 된 값은 상태와 이유, 관련 항목(설명 → 함정 → 업무 규칙) |
| 검색 | `Search`, `SearchController` | 본문 `h2` 절을 BM25로 찾는다 |
| MCP | `Mcp` | 조회 3개, `search_docs`, `get_page`를 Streamable HTTP(무상태)로 연다 |
| 질의응답 | `Ask`, `OpenAiModel` | 검색 → 모델 한 번 → 인용 검사 → 답 또는 보류 |
| 꾸미기 | `Decor`, `style.css`, `app.js` | 근거 링크·접기, 상태 배지, 흐름 상자, 절 접기. 본문 글자는 바꾸지 않는다 |

현재 출력: 서비스 8, 엔드포인트 72, Feign 호출 17, Kafka 발행 13·구독 9, 핸들러 연결(`calls`) 42, 발행↔구독 연결 9, 항목 221(설명 94·업무 규칙 59·함정 68), 경고 13(`kafka-topics` 11, `handler-calls` 2). 테스트는 검증기 24개, 서버 34개다.

## 2. 6단계: 조회 계층과 본문

| 이슈 | 결과 |
|---|---|
| [#27](https://github.com/MCshin00/hotdealwave-handover/issues/27) | 엔드포인트마다 응답 확인 상태(`responseCheck`: 응답 기록 있음·호출 못 함·코드만, HTTP 코드, 이유, 원문 줄). 72개 중 응답 기록 있음 61(200 48, 201 8, 400 1, 404 2, 500 2), 호출 못 함 11 |
| [#30](https://github.com/MCshin00/hotdealwave-handover/issues/30) | 관계 파일에 `calls`를 더했다. 엔드포인트·Kafka 구독에서 같은 서비스의 Feign 호출·발행까지의 사슬이다. 추출 Skill 관계 단계를 다시 돌려 42개를 채웠고 모두 확인됨이다. 부르는 곳 없는 Feign 호출 2개는 `handler-calls` 경고다 |
| [#28](https://github.com/MCshin00/hotdealwave-handover/issues/28) | `server` 모듈. 조회 3개와 엔드포인트·토픽·서비스 본문 |

`trace_flow`는 `calls` → Feign 대상 → 발행↔구독 연결 → 구독 핸들러의 `calls` 순으로 따라간다. 이어지지 않는 발행에서는 "확인 안 됨"과 `kafka-topics` 경고 이유를 붙이고 멈춘다. 대표 사례는 `createOrder`다. Feign 호출 4개와 대상 엔드포인트까지 이어지고, `requestProduct` 발행에서 멈춘다(같은 환경변수 `KAFKA_REQUEST_PRODUCT_TOPIC`을 쓰는 구독이 없음).

본문은 처음부터 텍스트로 정했다. 같은 본문을 사람·검색·모델이 읽으므로, 값·상태·근거가 글자로 있어야 어느 쪽에서도 빠지지 않는다. 토픽 페이지 주소는 환경변수 이름이고, 환경변수 없이 문자열로 적힌 토픽(`payment-dlq`, `product-dlq`)은 그 문자열이다.

## 3. 7단계: 검색과 MCP

[#33](https://github.com/MCshin00/hotdealwave-handover/issues/33)의 결과다.

- **조각:** 페이지와 같은 템플릿을 렌더링한 텍스트를 `h2` 절로 나눈다. 모든 페이지에서 724개다.
- **토큰화:** 식별자는 통째로, 점·하이픈으로 이은 이름은 그 안의 식별자도 통째로, camelCase·snake_case 조각, 한국어는 두 글자씩 자른다. 처음에는 `createOrder` 검색에서 서비스 본문이 1위였다. `order-service.OrderController.createOrder`가 `createorder` 토큰을 내지 않았기 때문이고, 점 안의 식별자도 넣어 고쳤다.
- **필터:** 질문에 서비스 이름이나 종류 말(API·토픽·설정 등 고정 목록)이 있으면 그 범위부터 찾고, 결과가 없으면 종류부터 풀어 다시 찾는다.
- **결과:** 같은 페이지는 점수가 가장 높은 절 하나만 남기고 상위 5개를 낸다.
- **MCP:** 도구 5개의 결과는 페이지 본문과 같은 텍스트다. 서버 안에서 모델을 부르는 도구는 두지 않았다. 답은 클라이언트의 모델이 쓴다.

클라이언트 확인은 질문 하나("주문 생성 API를 부르면 어떤 서비스를 호출하고 Kafka로 무엇을 발행하는지, 이어지지 않는 곳은 이유까지")로 한 번씩 했다.

| 클라이언트 | 부른 도구 | 답 |
|---|---|---|
| Codex | `find_endpoint`, `trace_flow`, `find_subscribers`, `search_docs`, `find_subscribers` | Feign 호출 3곳과 `requestProduct` 발행을 `파일:줄`과 함께. 구독 연결은 "확정할 수 없음, 실제 미연결이 입증된 것은 아님" |
| Claude Code | `find_endpoint`, `find_subscribers` | Feign 호출 4개와 대상, `requestProduct` 발행을 `파일:줄`과 함께. 구독자는 "확인 안 됨"과 이유. AI 해석 항목은 "확정된 것은 아님"으로 구분 |

두 클라이언트 모두 "확인 안 됨"을 확인된 연결로 바꾸지 않았다. Codex는 Feign 호출을 3곳만 들었다.

## 4. 8단계: 질의응답

[#35](https://github.com/MCshin00/hotdealwave-handover/issues/35), [#37](https://github.com/MCshin00/hotdealwave-handover/issues/37)의 결과다.

`/api/ask`는 고정 RAG다. 질문 하나 → `search_docs` 상위 5개를 C1~C5로 → `gpt-6-luna` 한 번(추론 없음, 출력 상한 1500토큰, 답·인용 번호·보류의 정해진 형식) → 인용 검사 → 답 또는 보류다. 인용 검사는 인용 번호가 넘긴 조각에 있는지, 답의 `파일:줄`이 인용한 조각에 있는지를 본다. 검사에 걸린 답은 원문을 보여 주지 않는다. 질문당 호출이 한 번이라 비용을 미리 말할 수 있고, 같은 질문으로 다시 재기 쉽다.

### 처음 구현(#35)에서 드러난 문제

| 질문 | 결과 | 원인 |
|---|---|---|
| createOrder 요청 필드는? | 세 필드와 근거는 나왔지만 couponId에 없는 `@NotNull`을 붙임. 추론 low·medium도 같음 | 어노테이션 없는 필드가 빈칸이라 모델이 앞 줄을 따라 지어냄 |
| 주문 생성이 보내는 상품 요청 Kafka 메시지는 누가 받나? | "확인 안 됨"을 놓침 | 본문의 한국어가 AI 해석 항목에만 있어 흐름 절이 검색되지 않음. 상위 5개가 토픽의 업무 규칙·함정 절 |
| 결제 서비스 운영 DB 비밀번호는 뭐야? | 보류 | 저장소에 없는 값 |
| requestProduct가 보내는 메시지는 누가 받나? | 수신자 "확인 안 됨" 유지 | 코드 이름으로 물으면 흐름 절이 걸림 |

필드 질문은 절만 넘기면 요청 필드 표가 빠졌다. 그래서 엔드포인트 페이지는 찾은 절 대신 본문 전체를 넘겼다.

### 본문 표현을 고친 뒤(#37)

- 빈 필드를 "어노테이션 없음"으로 쓴다.
- 항목 종류 `설명`을 더했다. 업무 규칙 Skill이 엔드포인트·Kafka 발행·구독마다 하는 일을 한국어 한두 문장으로 썼다(94개, AI 해석, 미확인). 페이지 맨 위 "설명" 절에 나온다.
- 토픽 페이지도 본문 전체를 넘긴다. 연결 질문이 설명 절에 걸려도 발행·구독 연결의 확인 상태가 함께 가야 하기 때문이다.
- Kafka 연결 경고의 이유를 식별자 나열에서 문장으로 바꿨다. 전: `구독자 확인 안 됨: order-service, spring.kafka.topics.request-product, KAFKA_REQUEST_PRODUCT_TOPIC`. 후: `구독자 확인 안 됨: 같은 환경변수(KAFKA_REQUEST_PRODUCT_TOPIC)를 쓰는 구독을 찾지 못함. 토픽 실제 값은 저장소 밖 환경에서 정해짐 (order-service, spring.kafka.topics.request-product)`. 경고 수와 판정은 그대로다.

| 질문 | 결과 |
|---|---|
| createOrder 요청 필드는? | basketList·addressId `@NotNull`, couponId "검증 어노테이션 없음" |
| 주문 생성이 보내는 상품 요청 Kafka 메시지는 누가 받나?(경고 문장 변경 전) | "확인 안 됨"은 남았지만 이유가 빠짐. Codex와 Opus 리뷰 에이전트 모두 조건 미충족으로 봄 |
| 같은 질문(변경 후) | "확인 안 됨"과 두 이유(같은 환경변수를 쓰는 구독 없음, 토픽 실제 값은 저장소 밖), 근거 `OrderEventProducer.java:62`, `application.yml:15`, `docker-compose.yml:156` |

### 비용

| 이슈 | 호출 | 입력 / 출력 토큰 | 비용 |
|---|---:|---|---|
| #35 | 6 | 137,890 / 696 | 약 0.014달러 |
| #37 | 3 | 41,541 / 416 | 약 0.004달러 |

`gpt-6-luna` 입력은 100만 토큰당 0.10달러다. 엔드포인트·토픽 본문 전체를 넘겨 입력이 질문 한 번에 1만에서 2만 토큰이 됐고, 질문당 0.001에서 0.002달러다. 가장 큰 입력은 비밀번호 질문의 6만 7천 토큰이었다. 임베딩은 BM25가 표현 차이로 근거를 놓치는 경우가 9단계 채점에서 확인될 때만 더한다.

## 5. 8단계: 페이지

[#39](https://github.com/MCshin00/hotdealwave-handover/issues/39)에서 문서 페이지를 꾸몄다. 근거 `파일:줄`은 고정 커밋 `cc43016`의 GitHub 원본 줄과 응답 원문 페이지(`/responses/{파일}`)의 그 줄로 링크해, 근거를 확인하려고 파일을 찾아 열 필요가 없다. 꾸미기는 렌더링 뒤 브라우저에 보낼 때만 덧씌우므로(`Decor`) 검색·MCP·모델이 읽는 본문 글자는 바뀌지 않는다. 전후 724개 절 텍스트를 비교해 차이가 없었다.

## 7. 한계

- 인용 검사는 답에 적힌 `파일:줄`이 인용한 조각에 있는지만 본다. 내용이 틀린 답, 근거를 적지 않은 답은 막지 못한다.
- 실제 호출은 대표 질문 몇 개로만 했다. 질문 종류별 정확도는 9단계 비교 실험에서 잰다.
- 검색은 BM25만 쓴다. 한국어 질문은 설명 94개에 기대고, 설명은 AI 해석(미확인)이다.
- 서비스 페이지는 여전히 걸린 절만 모델에 넘긴다.
- MCP 클라이언트 확인은 클라이언트마다 질문 하나다.

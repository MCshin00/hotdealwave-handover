# 비교 실험 보고서: 저장소 없이 문서로 답하기

9단계의 결과다. "서비스가 떠 있고 문서가 없음" 상황에서, 저장소 없이 이 도구의 문서로 답하는 쪽(MCP, 질의응답)이 코드를 가진 에이전트(기준선)만큼 맞게, 확인 범위까지 밝혀 답하는지 최종 질문 21개로 쟀다. 조건과 채점 방식의 결정은 [결정 문서 "비교 실험"](../decisions.md#비교-실험)에 있다.

## 1. 요약

| 조건 | 맞음 | 부분 | 틀림 | 확인 범위 밝힘 | 걸린 시간(중앙값) |
|---|---|---|---|---|---|
| 기준선(저장소 + Codex) | 21 | 0 | 0 | 20 (일부 1) | 71초 |
| MCP(저장소 없음 + Codex) | 12 | 9 | 0 | 21 | 49초 |
| 질의응답(`/api/ask`) | 6 | 11 | 4 | 20 (일부 1) | 4초 |

- 저장소를 가진 에이전트는 이미 모든 질문에 맞게 답했다.
- MCP는 저장소 없이 틀린 답이 없었고, 확인 안 된 것을 확인된 것처럼 말한 답도 없었다. 부분 9개 가운데 7개는 문서에 그 내용이 없어서다.
- 질의응답의 틀림 4개는 모두 보류한 답이다. 3개(Q04, Q14, Q19)는 문서에 있는 내용을 검색이 주지 못했고, Q20은 Gateway의 401 처리가 문서에 없었다. 확인 안 된 토픽 연결을 전제로 설명한 답이 1개(Q01) 있었다.
- 빠진 내용은 오류 응답 본문, 페이지 직렬화 설정, 배포 워크플로처럼 아직 추출하지 않은 것에 몰렸다. API를 쓰는 쪽이 가장 먼저 찾는 오류 본문이 비어 있다.

## 2. 실험 조건

| 조건 | 답을 쓰는 쪽 | 쓰는 것 |
|---|---|---|
| 기준선 | Codex(`gpt-6-astra`, 추론 high) | 원본 저장소의 깨끗한 체크아웃(`cc43016`) |
| MCP | 같은 Codex 설정 | 원본 코드가 없는 작업 폴더와 `/mcp` 도구 5개 |
| 질의응답 | `/api/ask`(`gpt-6-luna`) | 검색 상위 5개 절(엔드포인트·토픽 페이지는 본문 전체) |

- 질문은 개발자가 실험 전에 쓰고 고정했다(`eval/questions/final.csv`, 21개). 연습 질문 2개(`tuning.csv`)로 설정과 시간 제한(5분)을 먼저 정했다.
- 기준선과 MCP는 질문마다 새 세션에서 읽기 전용으로 돌렸다. MCP 지시문은 저장소가 없다는 것과 `hotdealwave` 도구로 분석 문서를 볼 수 있다는 것만 알린다.
- 시간 초과는 없었다.

## 3. 채점 방식

| 단계 | 하는 것 | 결과 |
|---|---|---|
| 기계 검사 | 답의 `파일:줄`이 고정 커밋에 있는지 | `eval/results/final/check.csv` |
| AI 교차 채점 | 새 Codex 세션과 새 Opus 세션이 조건 이름을 A·B·C로 바꾼 세 답을 고정 커밋과 대조해 정확도·확인 범위를 매김 | `grades/codex/`, `grades/opus/`, `grades/review.md` |
| 판정 | 갈린 답과 무작위 표본을 코드와 함께 보고 정함 | `grades/judgments.csv`, `grades/judge-*.md` |
| 최종값 | 판정한 칸은 판정값, 나머지는 두 채점이 같은 값 | `grades/grades.csv` |

- AI 교차 채점에서 63칸 가운데 19칸이 갈렸다(정확도 9칸, 확인 범위 16칸, 겹침 포함). 채점 한 번은 Codex 중앙값 66초, Opus 42초였다.
- 판정 기준은 개발자가 정했다. 정확도는 질문을 항목으로 나눠 코드와 맞추고, 질문이 묻지 않은 것은 요구하지 않는다. 확인 범위는 확인 안 된 것을 확인된 것처럼 말했을 때만 깎는다.
- 판정은 27칸이다.
  - 개발자가 3칸을 직접 정했다(Q04 MCP, Q06 질의응답, Q13 MCP).
  - 나머지 24칸은 새 Opus 세션이 판정하고, Codex 세션이 두 번 반박하고, Opus가 최종 의견을 낸 뒤 개발자가 승인했다. 반박으로 6칸이 바뀌었다(Q09·Q13·Q15·Q17·Q21 질의응답, Q21 MCP).
- 판정이 두 AI가 같았던 값을 바꾼 곳은 4칸이다(정확도 Q13·Q17 질의응답, 확인 범위 Q08·Q13 질의응답).

## 4. 결과

### 실행 비용

| 조건 | 시간(중앙값 / 최대) | 도구·명령 | 입력 토큰(캐시 제외) / 출력 토큰 | 인용(전체 / 고정 커밋에 없음) |
|---|---|---|---|---|
| 기준선 | 71초 / 91초 | 셸 명령 182 | 645,517 / 48,154 | 531 / 1 |
| MCP | 49초 / 74초 | 셸 명령 0, 도구 성공 241(`search_docs` 139, `get_page` 84, `trace_flow` 8, `find_endpoint` 6, `find_subscribers` 4)·결과 없음 26 | 513,814 / 34,861 | 580 / 2 |
| 질의응답 | 4초 / 12초 | 모델 한 번, 답 13·보류 8 | 620,312 / 5,462 | 85 / 0 |

고정 커밋에 없는 인용 3건은 모두 검사기가 잘못 읽은 것이다(기준선 1건은 호스트:포트 `smtp.gmail.com:587`을 파일 인용으로 읽음). MCP는 지시한 대로 셸 명령 없이 도구만으로 답했고, 대부분 `search_docs`로 찾고 `get_page`로 본문을 읽었다.

### 질문 묶음별

질문 문장이 묻는 것으로 나눴다.

| 묶음 | 질문 | 기준선 | MCP | 질의응답 |
|---|---|---|---|---|
| API 요청·응답·오류 | Q05, Q10, Q14, Q18, Q20 | 맞음 5 | 맞음 1, 부분 4 | 부분 3, 틀림 2 |
| 서비스 사이 흐름·처리 | Q01, Q02, Q06, Q07, Q08, Q11, Q12, Q15, Q16, Q19 | 맞음 10 | 맞음 7, 부분 3 | 맞음 3, 부분 6, 틀림 1 |
| 배포·운영·외부 설정 | Q03, Q04, Q09, Q13, Q17, Q21 | 맞음 6 | 맞음 4, 부분 2 | 맞음 3, 부분 2, 틀림 1 |

MCP가 가장 약한 곳은 API 응답 형식이다. 상황 1에서 API를 쓰는 쪽에 가장 먼저 필요한 것이라 다음 개선 대상으로 삼는다. 배포·운영 질문 가운데 저장소 밖 사실을 묻는 질문(Q09 콘솔, Q17 메일 계정, Q21 Grafana)은 세 조건 모두 "저장소에 근거 없음"을 밝혀 맞음이었다.

### 맞음이 아닌 답의 원인

| 원인 | MCP | 질의응답 |
|---|---|---|
| 문서에 없음 | 7 | 6 |
| 검색에서 못 찾음 | — | 5 |
| 받은 문서에서 빠뜨림 | — | 4 |
| 문서에 있는데 답에 없음 | 1 | — |
| 답이 틀림 | 1 | 0 |

문서에 없던 내용은 일곱 가지다.

| 빠진 내용 | 질문 | 지금 추출에서 |
|---|---|---|
| 배포 워크플로(시크릿, ECR, EC2에서 Compose 실행) | Q03, Q13 | 뽑지 않음 |
| 오류 응답 본문(`ErrorResponseDto`)과 만료 뒤 발급의 404 | Q18 | 뽑지 않음 |
| 소유자가 다를 때의 오류 메시지 | Q10 | 상태 코드와 필드 이름까지만 |
| Gateway가 본문 없는 401로 바로 끝내는 처리 | Q19, Q20 | 뽑지 않음 |
| 페이지 직렬화 설정(`VIA_DTO`) | Q05 | 뽑지 않음 |
| ES 색인이 커밋 전 같은 트랜잭션 안에서 실행됨 | Q15 | 업무 규칙에 없음 |
| 주문 생성의 상품·주소 병렬 조회 | Q01 | 업무 규칙에 없음 |

- MCP의 "답이 틀림"(Q11)은 문서의 Kafka ID(`payment-service.updateOrderStatus`)를 메서드 이름으로 옮겨 쓴 것이다. 문서는 틀리지 않았다.
- 질의응답의 "검색에서 못 찾음"은 5개(Q04, Q07, Q12, Q14, Q19)이고, 그 가운데 3개(Q04, Q14, Q19)가 보류였다. 필요한 내용은 문서에 있었지만 상위 5개 절에 들지 않았다. 예를 들어 Q12의 재시도 0회 설정은 DLQ 복구 항목에 붙어 있어 받은 토픽 페이지에 없었다.
- "받은 문서에서 빠뜨림" 4개는 받은 페이지에 근거가 있었는데 답에 쓰지 않은 경우다(Q06의 락 획득 조건과 408 등).
- 칸마다의 원인과 메모는 판정한 칸은 `grades/judgments.csv`, 나머지는 `grades/causes.csv`에 있다.

## 5. 실험 중에 바꾼 것

| 문제 | 바꾼 것 | 이슈 |
|---|---|---|
| 안내 없이 MCP를 등록하면 Codex가 도구를 부르지 않음 | 지시문에 도구 안내 한 줄 | #41 |
| `approval_policy="never"`로 MCP 도구 호출이 모두 거절됨 | 이 서버 도구만 자동 승인하고 MCP 조건을 다시 실행 | #41 |
| 처음 MCP 조건은 체크아웃과 MCP를 함께 줌. 기준선보다 셸 명령은 41% 줄었지만 시간은 비슷하고 입력 토큰은 10% 늘어 이득이 없음 | 문제 상황을 두 경우로 나누고, MCP 조건을 원본 코드가 없는 작업 폴더로 다시 정함. 처음 결과는 `repo-mcp/`에 남김 | #43 |
| MCP 답이 경로를 줄여 써서 인용 102개가 "없음" | 지시문에 "저장소 루트 기준 경로 그대로"를 더해 다시 실행. 남은 "없음" 2개는 검사기 오독 | #43 |
| 검사기가 루트 파일 인용(`docker-compose.yml:32`)을 코드 이름으로 읽음. 이름 불일치는 한 줄에 주장이 여럿이면 맞는 근거도 불일치로 셈 | 루트 파일 인용을 이름에서 빼고, 이름 불일치는 비교에 쓰지 않음 | #43 |
| 채점자가 응답 근거 복사본을 읽지 못함(Python 3.14 `tempfile`이 소유자만 읽는 폴더를 만들어, 다른 사용자로 도는 Codex 샌드박스가 못 읽음) | 체크아웃 옆에 일반 폴더를 만들어 복사 | #45 |
| 채점 근거에 복사본의 절대경로가 섞임 | 저장 전에 복사본 경로를 지움 | #45 |
| 갈린 칸이 많고, 기준이 칸마다 다르게 적용됨 | 개발자가 기준을 정하고, Opus 판정·Codex 반박·Opus 최종으로 같은 기준을 끝까지 적용 | #45 |

## 6. 다음 할 일

1. 추출 범위를 넓힌다. 배포 워크플로, 오류 응답 본문과 Gateway의 거부 응답, 페이지 직렬화 설정을 근거 `파일:줄`과 함께 뽑는다. 모니터링 설정(Prometheus·Loki)도 같이 본다. 이번 질문에서는 Q21이 저장소 밖 사실이라 드러나지 않았지만, 저장소 안에 근거가 있는 설정이다.
2. 질의응답의 검색을 고친다. 필요한 내용이 문서에 있는데 상위 5개 절에 들지 않은 경우가 5개다.
3. 두 번째 대상(10단계)에 도구를 한 번 돌린다.

`repo-mcp` 결과는 채점하지 않았다. 저장소만 남은 상황은 이 실험으로 재지 않았다.
